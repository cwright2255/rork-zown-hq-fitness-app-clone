# Anny body-mesh service

Wraps the Anny parametric human body model (Apache 2.0, github.com/naver/anny)
behind a simple HTTP endpoint for Zown HQ's body scan feature.

**Status: written and reasoned through from Anny's real source, not yet
run.** The mapping logic (measurements -> phenotype values) was tested
directly and works correctly. The actual Anny model call has not been
executed anywhere yet - the sandbox this was built in couldn't install a
working PyTorch (the default PyPI wheel requires CUDA libraries even for
CPU use, confirmed directly; the CPU-only build lives on a domain outside
the sandbox's network access). Cloud Build has neither restriction, so
deploying this is also its first real test - expect to need at least one
round of fixes once real errors show up.

## What it does

`POST /generate-mesh` with a scan's measurements (height, weight, gender,
body fat %) returns a `.glb` 3D mesh file, generated by Anny from those
measurements mapped to its phenotype parameters.

## Deploying (from a GitHub Codespace, same pattern as the Firebase functions deploy)

This needs your Google Cloud credentials to authenticate - not something
that can be done from this side. Steps:

1. Open a Codespace on this repo (or any environment with a browser you can
   complete a login flow in - a Codespace worked well for the Firebase
   deploy earlier, so following the same pattern here).

2. Install the gcloud CLI if not already present:
   ```bash
   curl https://sdk.cloud.google.com | bash
   exec -l $SHELL
   ```

3. Authenticate (same `--no-localhost` pattern as the Firebase login - it
   prints a URL, you open it, sign in, paste the code back):
   ```bash
   gcloud auth login --no-launch-browser
   ```

4. Set the project to the same one Firebase already uses (Firebase projects
   *are* GCP projects under the hood, so this should already exist):
   ```bash
   gcloud config set project zown-3c512
   ```

5. Enable the Cloud Run and Cloud Build APIs if not already on (safe to run
   even if they're already enabled):
   ```bash
   gcloud services enable run.googleapis.com cloudbuild.googleapis.com
   ```

6. Deploy directly from source - Cloud Build handles the Docker build
   remotely, with full internet access, so the CPU-only torch index in
   requirements.txt should resolve cleanly there even though it couldn't be
   tested locally:
   ```bash
   cd anny-service
   gcloud run deploy anny-mesh-service \
     --source . \
     --region us-central1 \
     --allow-unauthenticated \
     --memory 4Gi \
     --cpu 2 \
     --timeout 600
   ```
   `--memory 4Gi` (raised from an initial 2Gi after real evidence, not a
   guess: a direct log from a female-gender request showed the process go
   completely silent - no error, no graceful shutdown message - partway
   through female-specific breast blend-shape computation, which is
   consistent with an out-of-memory kill rather than a clean timeout or
   exception). `--timeout 600` because the real, measured cold-start time
   (loading Anny's blend shape data on a fresh instance) has been
   80-100+ seconds in direct testing - the original 60s value used on the
   very first deploy was too short and caused a real, observed truncated
   response.
   `--allow-unauthenticated` for now since there's no auth wiring on the
   app side yet - **tighten this before any real user traffic reaches it**,
   this flag makes the endpoint public.

7. The command prints a service URL on success
   (`https://anny-mesh-service-xxxxx.us-central1.run.app`). Test it
   directly:
   ```bash
   curl https://YOUR-SERVICE-URL/health
   curl -X POST https://YOUR-SERVICE-URL/generate-mesh \
     -H "Content-Type: application/json" \
     -d '{"height_cm": 178, "weight_kg": 95, "gender": "male", "body_fat_percent": 22}' \
     --output test-mesh.glb
   ```
   Open `test-mesh.glb` in any glTF viewer (e.g. https://gltf-viewer.donmccurdy.com/)
   to see the actual generated mesh.

## Known open questions, honestly flagged

- **Cold start time**: unmeasured. Loading Anny's blend shape data for the
  first request on a fresh instance could be slow - worth timing once
  deployed, and possibly worth a Cloud Run minimum-instance setting if it's
  too slow for a good user experience (this costs money continuously,
  unlike pure pay-per-request).
- **Gender phenotype direction**: assumed 0.0=male, 1.0=female based on the
  order in Anny's own source (`["male", "female"]`), not yet visually
  confirmed against an actual rendered output.
- **Muscle-from-body-fat heuristic**: a rough, deliberately conservative
  guess, not a validated mapping. Worth revisiting once real meshes can
  actually be looked at.
- **App-side integration is not started**: this service existing doesn't
  connect to the app yet. That's a separate, follow-up piece of work -
  calling this endpoint from the results screen, loading the returned
  `.glb` via Three.js's GLTFLoader in place of the current local
  buildBodyMesh() call.
